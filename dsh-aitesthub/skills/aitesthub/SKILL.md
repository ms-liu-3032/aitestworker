# AITestHub 测试方法

## 先选运行模式

用户明确说“不连接 Hub”“本地”“离线”，或者尚未绑定 Hub 且只要求通用测试时，使用本地模式。先调用 `aitest_local_design_rules`，基于用户本轮需求与实际页面证据理解范围；合并会改变预期的澄清问题，然后先展示测试点，再设计独立可执行的用例。本地模式不调用 `aitest_prepare_case_design`，不读取或声称拥有 Hub 的 TOM、Wiki、正式用例和个人偏好，也不声称通过 Hub 校验。通过 `aitest_local_save_design` 保存本机设计，先存测试点时 `cases=[]`；补齐用例时带原 `id` 与 `expectedVersion` 更新，保留返回的用例 ID。所有事实标明来源，未知菜单或状态标为待确认。生成质量按下文“跨业务用例写作与交付检查”复核。

做本地 UI 自动化时，先从当前页面核实入口、控件、数据和断言；用 `aitest_local_set_mapping` 把 Playwright 映射存到对应本地用例，再调用 `aitest_run_local_ui`。映射步骤使用 `type`、`locator`、输入时的 `data`，可用 `waitFor` 等待业务状态、`waitForResponse` 等待已核实的请求；不在 Skill 中写业务选择器或接口路径。执行后向用户逐条报告 PASS/失败、失败步骤、截图和本地 `reportPath`，明确状态 `LOCAL_ONLY` 表示仅本机保存；原始 trace、事件和录屏也留在本机。定位失败可参考现场证据修订映射再跑，但不能因页面变化自动改断言或把失败说成通过。只有用户明确要求且完成 Hub 绑定与规则准备后，才另走 Hub 资产回写流程；本地草稿不会自动成为 Hub 草稿或正式用例。

用户明确要求“基于 Hub 项目/历史资产”时，必须按下文 Hub 准备流程。Hub 连接失败要报告失败，不把本地结果伪装成 Hub 结果。两种模式都由 DSH 管理模型调用；本地模式不需要 Hub 服务凭据。

## 项目资产回写

从浏览器或需求中核实的实现事实，可用 `aitest_propose_wiki` 提交项目级 Wiki 候选；角色、流程、状态和动作骨架可用 `aitest_propose_tom` 提交项目级 TOM 节点候选。创建关系前先用 `aitest_get_tom_relation_types` 读取合法枚举与节点方向，再用返回的节点 ID 调用 `aitest_propose_tom_relations`；不要猜 CONTAINS/DEPENDS_ON。控件定位事实用 `aitest_propose_locator_map` 存为待审核定位表。每条都要给出可核查的来源依据，必须先有本人的有效 `workSessionId`。提交结果只是待审核资产，不能声称已经进入系统级知识或已可供用例引用；Wiki 包和条目、TOM 节点及关系须分别经 Hub Web 审核生效。关系的两端节点须先审核激活。定位表审核后可用 `aitest_get_locator_map` 再读取，执行时仍需检查页面版本和定位是否有效，不把定位表误称为完整自动化脚本。不要拿 DSH 绑定凭据调用 `/api/wiki`、`/api/mini-tom` 或 `/api/admin` Web 接口，也不要让用户手工重录本可提交的候选内容。不得把当前项目的实现细节直接提交为跨项目或系统级规则；升级仍走 Hub 的逐级审核路径。

## 自动化资产与自愈

UI 写入链路仍需覆盖实际界面交互。对于同名按钮，优先使用稳定 `data-testid`；没有 testid 时，用 `locator.within` 限定在已确认的可见容器，再用 role 和精确名称定位。`nth` 仅在顺序已核实时使用。`waitBefore` 是定位可见性的超时，不是固定等待；业务状态用 `type=waitFor` 等待页面可观察结果。关键动作若触发异步请求，可在该资产的对应步骤配置 `waitForResponse`，填写从本次网络证据核实的站内路径、方法和状态，再检查页面状态；具体业务路径、按钮和断言都归属自动化资产，不能写进 Skill。禁止用页面内 JS 强制点击绕过正常交互。修订映射走候选版本，真实跑通并回写证据后再审核。

响应等待必须由同一步动作触发；HTTP 2xx 只说明传输成功，不能替代页面断言。某一步没有触发预期请求时记录该步失败，检查映射或产品交互，不把它自动归为定位器故障。抽屉、弹窗等容器必须在继续操作外层页面前确认已关闭；优先使用明确的关闭控件及状态检查，不把遮罩点击或 Escape 当作所有系统的通用关闭规则。

页面、接口路径、定位器、等待条件和断言都存在该用例的自动化映射；跨用例可复用的控件事实先提交项目定位表并经审核。DSH 可以读取映射和定位表，按资产 ID 提出新候选版本并运行验证，无需为某个业务修改 Hub 代码。Skill 只定义选择依据和验证流程。`aitest_run_auto_asset` 的 `headless` 默认为 false；用户明确要求无界面执行时传 true，模式切换会关闭空闲浏览器窗口，正在采集的会话不能切换。无界面仍须上传 trace、截图和录屏证据，不能因为看不到窗口就宣称通过。

`press` 调用 Playwright 的 locator.press，会先聚焦 `locator` 指向的元素，再发送 `data` 指定的按键；对 `body` 发送 Escape 不保证应用关闭弹窗，应优先定位实际关闭控件并等待容器 hidden。`by:text` 定位使用精确文本；断言的 `expected` 默认检查目标元素文本是否包含预期，也可在映射中设 `match=equals` 检查去掉首尾空白后的相等。断言定位必须恰好命中一个元素；多个匹配须缩小 `within` 作用域，或在顺序经证据确认后使用 `by:nth`。异步页面用 `waitFor` 或断言 `timeout` 等待可观察结果，不用固定 sleep。

候选版遇到浏览器关闭等环境故障时，保留该版为待验证并用相同 `versionNo` 重试；定位、断言或业务失败不得作为环境故障绕过。旧版服务已把环境失败候选标为 REJECTED 时，不直接重跑已舍弃版本；先读取其映射，再用 `aitest_revise_auto_asset` 按原资产 ID 复制成新的候选版，说明原因，保留原运行历史。`aitest_delete_auto_asset` 是带原因的归档操作，保留版本、运行与证据；不要为“清理列表”直接硬删资产。

每次 UI 或接口自动化执行结束后，按工具返回的 `result`、`status` 和 `reportPath` 向用户展示该条用例的通过/失败、证据或运行回写状态及本地报告位置；失败时说明失败步骤和原因，多条用例逐条列出，不把一次 PASS 概括成整批通过。UI 报告包含本次采集截图、耗时、失败步骤与回写状态；接口报告只展示脱敏请求和断言摘要，因未启动浏览器而没有截图，不得伪造图片。若返回 `reportError`，明确报告生成失败；`EVIDENCE_PENDING` 或 `RUN_WRITE_PENDING` 仍显示真实待处理状态，不能因为本地报告生成就声称 Hub 已存档。报告保存在本机采集目录，不把截图或业务路径附加到 Skill 或全局规则中。

自动化资产分 `UI` 和 `API`，同一条用例可各有一份映射。UI 继续使用页面、定位器和浏览器采集；接口自动化须在 `aitest_create_auto_asset` 指定 `assetType=API`，保存方法、站内相对路径、请求头/体模板、跨步骤提取变量，以及 HTTP 状态/响应头/JSON 路径断言。首次用 `aitest_run_api_asset` 指定版本号，在本机直接请求被测系统；日常仅复跑已验证且 Web 已审核的版本。接口执行不启动浏览器，不调用模型逐步发送请求；不能因为 HTTP 200 就判 PASS，必须核对每条断言。接口断言失败不得自行修改预期或套用 UI 定位器自愈，业务变化走完整版本修订与重新审核。映射不存认证值：请求头用 `secretRef`，请求体敏感字段用 `${secret:NAME}`；对应 `AITESTHUB_API_SECRET_NAME` 须由本机 DSH 运行环境提供，不能让用户把密钥贴进聊天或测试参数。接口证据只保存状态、路径模板、请求/响应哈希、耗时和断言结果，不回写完整认证请求/响应体。若返回 `EVIDENCE_PENDING`，用原 `evidencePayload` 调 `aitest_record_api_evidence`，将返回的 id 放入原 `runPayload.apiEvidenceId` 后调 `aitest_record_auto_run`；若返回 `RUN_WRITE_PENDING`，直接用原 `runPayload` 重试。两种待处理状态都不能声称结果已落库。

执行验证与审核是两件事：首次执行映射或人工修订版跑通后，在 Hub Web 的“自动化资产”页面审核当前版本，可勾选多项批量审核。正式资产的每次自愈仍需人工审核；已审核的个人草稿资产仅改定位的自愈版在原始证据上传、候选版 PASS 后由 Hub 自动通过。只有 `status=VERIFIED` 且 `reviewStatus=APPROVED` 才能日常免模型复跑或发布跨项目复用。用户要求修改某条映射时，先按唯一 `assetId` 读取资产和当前版本，再用 `aitest_revise_auto_asset` 生成待验证的新版本，并执行验证；不要新建重复资产，也不要直接改旧版本。用户明确要求删除某条映射时，用 `aitest_delete_auto_asset` 按 `assetId` 舍弃，保留历史版本、运行和证据；不要删除归属的测试用例。用户撤销未跑通的修订候选时可用 `aitest_discard_auto_asset_candidate`，随后再提交新修订。DSH 不得自行审核正式资产。

L2 执行映射归属具体用例 ID，用 `aitest_create_auto_asset` 存为 v1 草稿，包含站内页面路径、顺序步骤、运行时测试数据参数和可观察断言；不得当作 Wiki 正文或只存 Excel。版本、`verified`、`healCount` 由 Hub 管理，不写进映射。首次传 `versionNo=1` 调 `aitest_run_auto_asset` 跑通并回写原始证据后才变成 VERIFIED；以后读取当前 VERIFIED 版并调用一次执行工具，不逐步让模型重新推理。运行时依次尝试主定位与最多 4 个备用定位，只有全部定位失败才让模型参与；运行失败后只在结果为 `LOCATOR_FAILURE` 时读取失败用例、当前版本和现场证据，使用 `aitest_propose_auto_heal` 仅修改 locator，并显式执行候选版本。Hub 自动保留并去重最近的定位分支，最多 4 个备用分支；候选未跑通则保留旧版。自愈次数用于观察，不再按累计次数阻断；频繁修复时应补稳定锚点。断言、环境、数据冲突或业务失败不得自动改预期。跨项目发布只由 Web 项目管理者操作，并冻结已验证正式用例的指定版本。若返回 `EVIDENCE_PENDING`，先用 `aitest_capture_stop` 重试上传，再用返回的同一个 `runPayload` 调 `aitest_record_auto_run`；若返回 `RUN_WRITE_PENDING`，直接用返回的同一个 `runPayload` 重试 `aitest_record_auto_run`。两种待处理状态都不能声称运行结果已落库。测试数据使用项目认可的受控账号与数据，映射只保存参数名，不硬编码真实个人信息；不得把某种位数、格式或前缀默认视为不会触发真实通知。修改原有用例草稿时，先用 `aitest_get_case_draft_revision` 读版本，再用 `aitest_revise_case_draft` 原位修订；不要因修改一条用例而新建多份草稿。
创建 L2 的字段必须精确：`steps[*].type` 是动作，`steps[*].locator` 使用 `by/value`（nth 使用 `by/base/index`），输入步骤用 `data`；`assertions[*].locator` 同样使用 `by/value`，可选文本预期字段为 `expected`。不得用 `action`、步骤级 `value` 或 `expect` 替代。先读取归属草稿或正式用例的准确 `caseNo`，不能从标题猜编号。
修改已经在本地用例库的用例时，先从 `aitest_list_my_drafts` 找到该条的唯一 `id`，再用 `aitest_get_local_case` 读取全文和 `versionNo`；调用 `aitest_update_local_case` 以同一 `localCaseId`、`expectedVersion` 和稳定 `requestKey` 原位更新。正 ID 是普通草稿，负 ID 是轨迹草稿。标题相同不代表 ID 相同，不能按标题批量覆盖或为一次修订调用新建草稿工具。仅修改本人未提交的用例；更新后再次读取该 ID 核对内容和版本。正式用例仍走原审核流程。
若自动化资产返回 `caseMissing=true`，说明归属用例已不存在；不能审核、复验或自愈，应保留历史证据并舍弃旧资产，再对现有用例建立映射。若返回 `caseStale=true` 且 `caseMissing=false`，说明归属用例已改版；停止旧映射直跑，也不得通过“只改定位”掩盖业务步骤变化。Web 可复制当前映射生成复验候选版，DSH 对候选版本重新执行验证后才更新当前版；已有旧的定位自愈候选须先舍弃。定位链优先使用稳定的 testid/角色/标签/placeholder，必要时补文本和作用域选择器；`nth` 仅在已确认顺序稳定时使用，不固化 CSS Modules 哈希类名。

## 用例独立执行原则

每一条用例都必须能单独执行，不能默认前面的用例已执行、通过或留下数据，也不能写“沿用上一条用例的结果”。若需要已知账号、开关、人员、页面状态或业务数据，在本条前置条件中写清可独立准备的具体条件；若必须通过操作建立状态，把准备操作写进本条步骤，从已确认入口一直写到验证结果。用例顺序只用于阅读和组织覆盖，不构成执行依赖。生成每批用例后随机打乱阅读顺序复核：单独拿出任一条，测试人员仍能按前置条件和步骤执行；否则补齐本条后再提交 Hub 校验。对于确需共享昂贵环境准备的场景，可以复用命名明确、可重复执行的测试数据准备流程，但本条必须写明其输入、目标状态和核验方式，不能只引用另一条用例编号。

## 与 Web 用例质量对齐

Web 端按用例编排项逐批生成并校验，DSH 也应先把每组测试点拆成明确的验证目标：本组用什么角色和数据、从哪个入口开始、经过哪些真实业务动作、在何处观察结果，以及哪些边界或异常要分别写。然后才写用例，不把覆盖计划的标签直接翻译成标题。每个业务模块写作前，先用 `aitest_search_historical_style_examples` 按已确认的模块或页面词取 3–5 条有完整步骤和预期的导入用例；预取的最近 8 条没有按模块过滤，不能直接当作当前模块风格依据。只有相关且完整的历史样例才能用于标题、菜单措辞和步骤颗粒度参考；事实与预期仍以本轮需求、已审核 Wiki 正文和真实页面为准。相关样例为空时继续依据已确认事实写，并说明风格样例缺口。

每组候选提交 `aitest_validate_case_batch` 之前，逐条做人工可执行性检查：单独交给不读聊天记录的测试人员，前置条件是否能准备、入口是否明确、字段/按钮/测试数据是否具体、每一步预期是否在该步之后可观察、是否存在未证实的菜单文案或状态、是否默认上一条用例留下数据。任一项有缺口，先修这条，再提交后台校验。后台通过只证明结构和覆盖义务满足，不代表真实业务语义已经核对；不要把“校验通过”当成免复核许可。

对于需要既存对象或状态的场景，本条用例须写明可独立准备的对象、状态和数据，或在本条步骤中从已确认入口建立它们；不能默认上一条用例已运行。业务术语、角色与状态以本轮已确认的 TOM、Wiki 和需求为准。

1. 用户明确要求创建新项目时，调用 `aitest_create_project`，把创建结果和项目 ID 用普通对话告知用户；已有项目用 `aitest_list_projects` 查找并确认项目 ID。不要跨项目混用资产。继续旧任务时读取已保存的 TOM 模式和阶段，不重复提问。
2. 收到 AITestHub 项目需求时，先确认项目 ID；若 Hub 项目接口不可用，立即说明连接失败并停止本轮 Hub 用例设计，不能离线编写一批“待入库”用例。先读取项目上下文以识别阻断性事实冲突，把会改变范围、预期或安全边界的问题合并成一轮，同时问用户本轮采用“项目和系统 TOM / 仅项目 TOM / 不使用 TOM”哪一种；已明确指定的选项不再问。一般细节标为假设，避免逐项反问。取得明确选择和阻断项回答后，**先调用 `aitest_prepare_case_design`**，传原始需求全文和 TOM 模式；只有它返回 `ready:true`，才调用 `aitest_start_work` 并开始测试点/用例推演。准备结果已经包含当前项目事实、设计规则、所选 TOM、已审核生效 Wiki 概况、少量历史用例和本人偏好；不要拿本地记忆或旧缓存代替。Wiki 概况只含至多 500 字的摘要，不能当成完整规则。按需求业务词调用 `aitest_search_wiki`，再对相关 `entryId` 调用 `aitest_get_wiki_entry` 读取完整正文；摘要找不到完整规则时说明尚未确认。准备结果中的 `formalCases` 是按本轮 TOM/需求词检索的至多 8 条辅助用例，含完整步骤与预期；若需查重或核对覆盖，按模块或关键词继续调用 `aitest_get_test_cases`，必要时按 `id` 调用 `aitest_get_test_case_detail`。引用规则或历史用例时记录已读的来源 ID，不得只凭标题、摘要或最近 8 条判断覆盖情况。分别报告 TOM 可用/选中数、关系数、关联 Wiki 数、未关联 Wiki 候选数、正式用例样本数与 `importedHistoricalExamples` 样例数；不得由正式用例样本为空推断正式库为空，也不得由通用资产搜索没有 Wiki 结果推断 Wiki 为空。只有 Wiki 接口返回可用条目总数为零时才说当前可见的已审核生效 Wiki 为零。TOM 暴露新的关键冲突时可补问一次；未解决的阻断项不能擅自确定预期。
3. 先保存 `REQUIREMENT_ANALYSIS`，再将澄清问题、用户回答和保留假设存入 `CLARIFICATION`；无阻断问题时用空 `answers` 数组。**先生成并展示测试点，不要直接展示测试用例。** `TEST_POINTS.points` 每项必须有唯一 `id`（TP1、TP2…）、`title`、`pointType`（取设计规则返回的类型）、`scopeDecision`（GENERATE/REFERENCE_ONLY/EXCLUDED）、非空 `sourceBasis`；不生成时还要有 `scopeReason`。保存后用普通对话展示测试点、来源、类型与缺口，等待用户反馈或“继续”。汇报数量、分布和导出工作表时从保存结果或实际文件统计，不能凭印象推断；区分所有测试点与本批生成测试点。
4. 根据确认后的测试点保存 `COVERAGE_PLAN.items`：每个 GENERATE 测试点恰好一项，含 `pointId`、`designMethods` 和 `coverageRequirements`，必须包含 Hub 原有设计规则对该类型的全部义务。生成 `CASE_DESIGN.cases` 时，每条含 `caseTitle`、`moduleName`、可空 `precondition`、`steps`、`expectedResult`、`caseStrategy`（NODE_FOCUSED/FLOW_COMPOSED）、`scenarioType`、`sourceTestPointRefs`、`designMethods`、`designCoverage`、`sourceBasis`、`unsupportedItems`、`confidence`。按最多 5 个测试点为一组调用 `aitest_validate_case_batch` **提前校验候选用例**，一组通过再处理下一组；失败只修正该组，绝不先写完几十条后要求用户决定是否全部重写。所有组通过后合并并保存完整 `CASE_DESIGN`，再保存 `QUALITY_REVIEW`；这只是内部校验分组，不分批向用户征询写入方式。所有待生成测试点都要有用例覆盖其方法、义务和场景类型；不能只给一条正向代表用例。按 `writingStandard` 的七栏呈现：用例名称、所属模块、标签、前置条件、备注、步骤描述、预期结果。标题用业务语言写明操作和结果；模块按 `/页面/功能/子功能` 层级写。标签和备注没有真实内容就留空。前置条件只写执行前必须具备的开关、账号、人员或数据，不把操作步骤塞进去。原子检查可以只有一步；完整流程按真实操作分步，不为了凑数增加点击。步骤必须从已确认的入口或明确的前置页面开始，按“进入页面或打开弹窗 → 选择对象、填入具体数据 → 提交或触发验证”的真实顺序写到被检查结果；只写“在新增页输入后提交”而未交代如何到达该页，且前置条件也未说明时，不可执行。每步明确页面/弹窗、按钮/字段、动作和必要数据；每项预期逐条写出可观察的页面、提示、字段值或记录状态，不能只写“选择成功”“保存成功”“符合预期”。步骤和预期从 1 连续编号、逐条对应，保存时用换行分隔，表格展示可用 `<br>`。模板里编号跳号或“更新姓名”却预期“成功删除”等笔误要纠正，不能照抄。节点用例将前置节点写进 `precondition`，完整流程用例按依赖顺序写步骤。后台拒绝时修订对应阶段，不绕过校验；Hub 中断时停止并说明尚未保存的内容。
5. 用例业务事实和术语来自本轮已命中的 TOM、知识与项目上下文。`aitest_prepare_case_design` 返回的 `importedHistoricalExamples` 是基础项目或当前项目手动导入的真实历史用例，只用来学习标题、具体操作步骤和逐步预期的写作风格；`formalCases` 用于查重和增量范围。若未返回样例，明确说明无法模仿历史风格，不得臆造。模仿表达方式，不照抄旧用例、不引入旧需求事实。再参考 `aitest_get_my_style` 中本人的偏好；个人偏好不能覆盖事实、强制方法或证据。避免程序变量名、内部 TP/CP/CD 编号、空泛 AI 套话进入用户可见正文。用户可用 `/aitest-style` 修改；若多次修订或明确要求优化习惯，用 `aitest_propose_style` 提出带依据的候选，由本人查看并接受后才生效，不得扩散到其他用户。
6. 按顺序保存以上阶段后，少量用例可逐条调用 `aitest_save_case_draft`；多条用例用 `aitest_save_case_batch` 一次提交最多 100 条，各条仍保留独立标题、前置、步骤、预期、来源和幂等键。可同时附各自的 UI/API 映射；后台按新草稿 ID 建立一对一资产，整批失败会回滚。标题、所属模块、前置条件、步骤和预期必须与已通过后台校验的 `CASE_DESIGN` 一致。传入本轮 `workSessionId`；来源只记录检索结果中的真实 ID，来源不明传空数组。同一条重试沿用原幂等键，不同用例使用不同键。不能只为减少工具调用就把不同可独立判定的场景硬合成一条。批量写入不等于批量验证运行或审核；每份执行映射仍须单独真实跑通并保留证据。用户提出修改时先修订受影响的阶段，随后更新草稿；上游变化会使下游快照过期。保存只代表个人草稿写入，不能宣称已审核或进入正式库。
7. 浏览器主动执行：调用 `aitest_capture_start` 打开本机 Chromium；要关联用例时传本轮 `workSessionId`。用 `aitest_browser_action` 的 `navigate/click/fill/press/select/check/uncheck/inspect` 在同一页面操作，用 `assertText/assertVisible` 检查预期；断言失败也要停止采集并上传证据，不能把失败说成通过。结束时调用 `aitest_capture_stop` 上传 DOM 事件、网络、截图、Playwright trace 和 CDP 录屏帧。保存关联用例时传已完成的 `captureSessionId`。人工被动采集：请使用者运行 `/aitest-capture-start <项目ID> <URL> [任务ID]`，在打开的窗口手动测试，最后运行 `/aitest-capture-stop <项目ID> <会话ID>`。每个登录身份分别启动采集会话。证据上传失败时重试停止命令；只有收到远程完成结果才报告保存成功。`/aitest-capture-evidence` 可查看远程证据清单。检查页面状态与实际结果，以工具生成的原始证据为准，不从聊天描述推断执行成功。
8. 正式用例仍由提交人审核后才进入正式库。DSH 用普通对话展示完整草稿，请用户明确决定是否提交；当前正式提交仍使用本人命令或原 Web 审核页，不能由模型自行调用正式提交接口。不要在普通测试对话中要求用户逐阶段输入命令。Agent 委托凭据用于读资产、写草稿和采集证据；项目创建工具使用绑定用户身份，且仅在用户明确要求时调用。
9. 普通需求分析、测试点、用例设计和浏览器采集都使用本插件的共享工具及 Hub 资产，**不在当前本地项目文件夹生成 `.py` 文件**。仅在用户明确要求可执行的 Python 自动化脚本或导出文件时创建文件，并说明用途与位置。UI 自动化优先复用本插件的 Playwright 能力和 Hub 的用例/证据，不为每个项目复制一套采集脚本。
10. 汇报已有草稿时，不能把“写入草稿库”说成“符合当前 Hub 方法论并可直接执行”。尤其是旧版本流程生成的草稿，先按当前规则检查测试点覆盖、逐步操作和逐步可观察预期，再提出执行；有缺口就明确缺口和修订建议。已排除的范围只有用户改变范围决定后才进入用例设计。给用户一个自然语言的下一步建议，不要求在补缺口、开启排除范围和执行未复核草稿之间做无关的多选。

11. 用户限定“只汇报来源 ID 与数量、不生成”时，汇报完即停，不附加“每点一条/补边界/直接执行”等选项。用户要求设计测试点或用例时，按已确认需求和来源继续相应阶段；ROLE 或关系缺失不禁止使用已确认需求，但必须把角色边界的 `sourceBasis` 标成需求条款，不冒充 TOM。`COVERAGE_PLAN` 对每个测试点是一项计划，**不是一个测试点只能写一条用例**；根据等价类、边界值、状态迁移、角色与异常路径派生所需的多个可执行场景，允许一条完整流程用例覆盖多个点，逐项核对覆盖义务。未知的菜单、提示和状态先列为待确认，不能靠增加用例数量掩盖证据缺口。只有用户明确要求执行且已确定被测地址、可用账号/环境、执行范围后才开始浏览器采集；来源审计结果或未复核的旧草稿不能作为“直接执行”的依据。不要把自然语言任务变成让用户在编号菜单中选下一步。

## TOM 骨架、Wiki 语义与正式用例的使用顺序

`aitest_prepare_case_design` 返回的 `designContext` 是本轮事实入口。先读 `tomNodes` 中的角色、流程、动作、状态等逻辑对象，再沿 `tomRelations` 理解谁可以做什么、步骤依赖和状态如何变化。先看 `tomTypeCoverage` 的 available/matched/selected：若 ROLE、STATE 或 FLOW 可用但本轮未命中，自己用需求里的角色名、状态名和相关业务词再次调用 `aitest_get_design_context` 补查；不要把补查问题转交用户选择。比较 `tomConfirmedRelationAvailableCount` 和本轮 `tomRelations` 数量：前者大于 0 而后者为 0 是检索范围缺口；两者都为 0 才说明当前可见 TOM 缺少已确认关系。任何情况下不得从相邻名称推断状态迁移或角色权限，也不得称孤立节点足以构成完整骨架。`tomNodes` 的 `projectId`/`sourceProjectId` 可帮助定位系统对象的来源项目。`wikiLinked` 是与这些 TOM 对象人工关联且已审核生效的语义/实现正文，读取其完整内容后再确定业务术语、页面表达、限制和例外；不得把 TOM 名称直接扩写成具体界面事实。`wikiSearchFallback` 返回多个业务词的 `queries` 与去重候选；逐个看匹配数，读取相关 `entryId` 的完整正文，并用 `aitest_search_wiki` 补查需求原文中的关键业务词。未关联 Wiki 只能作为候选，即使正文相关，也不能声称它与 TOM 已关联。若一条窄词命中 0，而 `availableByScope` 非零，必须继续换业务词，不得说 Wiki 缺失。正式用例放在最后，用于覆盖核对、可执行步骤与本人/项目写法参考；历史用例与已审核 TOM/Wiki 冲突时标出冲突，不能让旧用例覆盖当前规则。输出测试点和用例时保留关键 TOM ID、关系 ID、Wiki 条目 ID 与正式用例 ID，明确哪些事实尚未关联或未证实。

读取 Wiki 时看 `evidenceRole` 和 `sourceType`：`HISTORICAL_COVERAGE_ONLY`、`HISTORY`、`IMPORTED_HISTORICAL_CASE` 与 `FORMAL_TEST_CASE` 是历史覆盖证据，不是当前界面语义或实现规则；其步骤/前置为空时也不能作为写法样例。优先检索并阅读 `SEMANTIC_KNOWLEDGE` 的规则、实现、决策正文。历史用例的业务术语、状态或规则若与当前已确认来源冲突，按本项目确认口径写，并把冲突来源 ID 标清。若项目没有可用的正式用例或合格历史样例，不得声称会沿用其他项目的写法；使用当前 Hub 返回的写作标准和用户提供的格式。对来源清单只报实测数量：`tomRelations=0` 不能单独证明全库没有关系，必须同时报 `tomConfirmedRelationAvailableCount`；跨轮汇总时核对列表条数与声称的选中数。

## 写法依据

Hub 当前七栏结构为用例名称、所属模块、标签、前置条件、备注、步骤描述、预期结果。具体菜单、字段、提示和样例从当前项目已确认的需求、知识与历史用例读取；Skill 不保存任何项目的业务示例。导入或导出文件的列名、列数、状态值和责任人字段以目标系统或用户本次指定的模板为准，不把某个项目的 Excel 格式写成全局规则。

## 跨业务用例写作与交付检查

1. 先确定本条的业务对象、操作、预期变化和范围。标题用可区分的业务语言写出“对象 + 动作 + 可判断的结果”，同一测试点下不同场景用条件区分；不写“验证功能正常”之类空泛标题，也不把测试点编号、设计方法或内部用例号放进标题。明确排除的范围不生成；需求与现有实现冲突时单列差异，不能把已观察到的缺陷改写成通过预期。
2. 前置条件只记录执行前必须具备且可独立准备的账号角色、配置开关、既存对象与状态、设备及外部系统。需要操作才能建立的状态写进本条步骤。配置值与日期先读取当前项目口径；示例值标明是示例，时间尽量用相对边界，不能把一次项目数据写成通用常量。没有特殊条件就留空，不填“环境正常”套话。
3. 步骤从已确认的菜单、页面或明确的前置起点开始，按真实操作顺序写；每一步说明所在页面或容器、控件、动作和必要数据，省去“测试人员”之类主语。弹窗、抽屉、下拉和特殊提交动作必须按已核实的实际交互拆开，不能用“完成操作”概括。一步一项可执行动作；原子检查允许一步，完整流程写全，不按固定步数凑长。
4. 每一步配同序号的一项预期，必须是该步之后可观察的页面文本、字段值、记录状态、数量变化或外部系统结果；跨模块结果写明到哪里查看。数量断言写清基数或比较方式及增量。瞬时提示不能作为唯一通过依据，应补持久状态或记录；“成功”“符合预期”不能单独作为预期。步骤和预期逐项核对，不能把后续动作的结果写到前一步。
5. 测试数据使用项目认可的隔离数据，能标识测试来源并可清理；需要唯一值时说明生成和回收方式，不硬编码真实个人信息或未经确认的号码段。外部通知、支付或第三方链路须写明可用性和核验位置；环境未就绪且没有可判断的替代证据时标记阻断，不编造通过结果。
6. 保存前把每条用例单独交给不读聊天记录的人复核：前置可准备、入口可找到、步骤可逐个执行、每个预期可取证、术语与当前产品一致。抽查发现同类问题时修整整批，把未确认的词和修正记录到 `QUALITY_REVIEW.findings`。内部来源 ID、覆盖映射与执行状态留在 Hub 对应字段；用户要求 STEP 表格时，一行只放一步及其同序号预期，依目标模板导出，不在单元格里堆多个步骤，也不擅自增删目标列。

## 菜单文字与写作风格校准

项目样例是写法参考，不是通用菜单字典。真实用例从本轮需求、澄清、已审核的项目/复用/系统 Wiki、TOM 或浏览器实际页面提取菜单、按钮、字段和提示的原文。`moduleName` 的每一级使用已证实的界面称呼；若资料只说明业务模块而没有菜单，先问一轮或用浏览器核实，不把合理猜测写成事实。`sourceBasis` 记录术语来源，未确认的界面词放在 `unsupportedItems`，不能以高置信度保存。

正向用例必须列齐当前场景真正必填的输入；预期阻止提交时，不得接着写成自动跳转成功。项目样例只用于学习写法，不按字数或旧词机械替换；对 URL 参数、报错文案和菜单名称等缺来源的细节先核实，仍未证实就列为待确认项。
